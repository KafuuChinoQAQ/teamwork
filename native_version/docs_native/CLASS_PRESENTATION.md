# 课堂展示稿（native 版本）

> 展示主线：**不用任何外部工具，从 ELF 字节流一路做到控制流图。**

---

## 一、现场演示命令（6 条）

```bash
cd /home/kali/elfcfg

# 1. 手工编译（0 错误 0 警告）
gcc -x c++ -std=c++11 -O0 -g -Wall -Wextra -Wpedantic -I src \
    src/main.cpp src/core/*.cpp src/elf/*.cpp src/arch/*.cpp src/arch/x86/*.cpp \
    src/cfg/*.cpp src/analysis/*.cpp src/output/*.cpp -lstdc++ -o elfcfg

# 2. 先看 ELF 头部（全部由自己解析）
./elfcfg --info demo

# 3. 看我们自己的反汇编（不调用 objdump）
./elfcfg --disasm demo classify

# 4. 生成控制流图
./elfcfg demo classify > classify.dot
dot -Tpng classify.dot -o classify.png && xdg-open classify.png

# 5. 看统计与循环提示
./elfcfg --summary demo classify

# 6. 换成别的函数试试
./elfcfg --text demo loop_sum
```

## 二、3～5 分钟讲解顺序

### ① 这次和上一版的区别（20 秒）

> "上一版的程序是调用外部 objdump 拿反汇编，再自己分析。
> 这一版把 objdump 也去掉了 —— 从打开 ELF 文件、解析符号表、
> 解码机器指令，到划分基本块、连边、画图，全部是我们自己的代码。
> 整份代码不依赖 STL、不依赖任何第三方库，也没有 popen / system / exec。"

### ② 六个分层（40 秒）—— 指着 UML 图

> "程序分成六层：
> 最底下是文件访问层，用 `open`/`fstat`/`mmap` 把 ELF 映射进来；
> 上面是 ELF 解析层，自己解析文件头、节头表、字符串表、符号表；
> 再上面是**指令解码层**，这是这一版最关键的部分，从机器码字节
> 逐条解析出指令；然后是 CFG 层，划分基本块、连边、构成图；
> 最后是分析层和输出层。
> 每一层都是"抽象基类 + 派生类"，上层只认基类指针。"

### ③ ELF 解析（30 秒）—— 敲 `--info`

> "这是我们自己解析 ELF 文件头的结果：类型、架构、入口地址、
> 节数量、符号数量，全部来自我们对文件字节的直接解析。
> 校验了 magic、64 位、小端、x86-64 这四项。"

### ④ 自己解码机器码（60 秒）—— 敲 `--disasm`，这是重点

> "这是我们自己解码出来的反汇编。我们按 x86 的编码规则从字节开始解析：
> 先看有没有 legacy 前缀，再看 REX 前缀，然后是 opcode，
> 再根据 opcode 判断有没有 ModRM、要不要读 SIB、位移多长、立即数多长。
> 每一步都能算出这条指令到底几个字节。
>
> 我们对照过 objdump：classify 函数 26 条指令，
> **地址、助记符、操作数逐条完全一致**。
> 这个对照脚本在 tests/ 目录下，但程序本身绝不调用 objdump。"

### ⑤ 基本块与连边（40 秒）—— 敲 `--summary`

> "基本块用 Leader 法划分：函数第一条指令、跳转目标、跳转的下一条，
> 这三个位置是入口。26 条指令划成 9 个基本块。
>
> 连边只看每个基本块的最后一条指令：
> 条件跳转给两条边 —— 一条跳到目标，一条顺序落下；
> `jmp` 只给一条边，不再顺序执行；
> `ret` 不给边，函数在这里返回。
> 9 个块连出 11 条边。"

### ⑥ 分析 Pass 与结果（40 秒）—— 切到 CFG 图

> "CFG 建好之后跑三个分析 Pass：
> 可达性分析标记可达块；统计 Pass 统计指令数和指令构成；
> 循环提示 Pass 找出向低地址跳的边。
>
> 注意这里我说的是**向后跳转提示**，不是严格意义上的 back edge ——
> 严格判定需要支配关系，我们用的是地址比较这个演示性近似。
> 在这段代码里，B7 到 B6 这条红色加粗的边确实对应源码的 for 循环。"
>
> "对照源码看：B0 的 `jle` 对应 `if (x > 100)` 不成立、转入 else if；
> fall 边才对应条件成立；B7 的 `jle` 往回跳就是 for 循环；
> B8 是 `ret`，标红，没有出边。"

### ⑦ 收尾（20 秒）

> "整体大约 6000 行，49 个源文件，分成六层。
> 编译用一条 gcc 命令，0 错误 0 警告。
> 这一版的架构是为后续实验准备的：
> analysis 目录里已经预留了栈分析、数据流分析、污点分析、
> 危险函数识别这些接口，以后加新的分析只需要写一个派生类。"

## 三、老师可能追问的问题

### Q1：解码器支持多少指令？遇到不认识的怎么办？

> "控制流指令全部支持：16 种条件的短跳转和近跳转、`jmp`、
> `call`、`ret`、`loop`/`loope`/`loopne`/`jrcxz`、
> 以及 `FF /2`、`FF /4` 的间接调用和跳转。
> 数据传送和运算支持 `mov`、`lea`、`cmp`、`test`、`add`、`sub`、
> `and`、`or`、`xor`、`neg`、`push`、`pop`、`leave`、`nop` 等。
>
> 遇到不认识的 opcode，我们会**明确报错并停止**该函数的解码，
> 输出地址和 opcode 字节。绝不会把未知指令当成 1 字节继续解码 ——
> 那样后面全部会错位。"

### Q2：怎么证明你的解码是对的？

> "两个办法：
> 第一，用 tests/ 下的脚本和 GNU objdump 逐条比对，
> classify 和 main 都是 26/26 条指令的地址、助记符、操作数完全一致；
> 第二，CFG 结构也和上一版（用 objdump 的版本）逐边比对过，
> 11 条边的连接关系和标签完全一样。
>
> 需要强调的是，objdump 只在开发阶段作为对照工具，
> 程序运行时不会调用它。"

### Q3：有没有用 Capstone / LLVM / libelf？

> "没有。ELF 结构体用的是 Linux 系统头文件 `<elf.h>` 里的定义，
> 那只是数据布局的描述，不是解析库。
> 解析逻辑、解码逻辑全部是我们自己写的。"

### Q4：向后跳转边就是回边吗？

> "不是。严格意义的 CFG back edge 要求**目标块支配源块**，
> 需要先构造支配树。
> 我们用的是"目标地址 ≤ 源地址"这个判据，
> 属于**演示性近似**，所以代码和文档里统一叫它
> backward jump hint（向后跳转提示）。
> 在本例的 classify 中它确实对应 for 循环，但这是这个例子的情况，
> 不是普遍保证。"

### Q5：switch 语句能处理吗？

> "能识别出那里是间接跳转，但不能完整还原每个 case。
> 因为 GCC 会把 switch 编译成跳转表，用 `jmp *table(,%rax,8)`
> 实现。我们识别出这是间接跳转，但不会去读跳转表内容，
> 所以 CFG 在这里就断开了，那些 case 对应的块会被标成不可达。
> 这在 `--text demo switch_test` 的输出里能直接看到。
> 这是已知限制之一。"

### Q6：为什么不支持 STL？

> "题目要求。所以三张表全部用 struct + 指针 + 内存池手工组织，
> 动态数组也是自己写的 `SimpleVector<T>`，
> 字符串用 `char[]` 和 `<cstring>` 的函数。"

### Q7：内存是怎么管的？

> "指令、基本块、边这三类对象全部由 `MemoryArena` 分配，
> 按 64 KiB 分块，块内线性切分，分配即清零。
> 程序结束时一次性归还所有块。
> 这样既避免了几万次 malloc，也不存在漏 free 某条链表的问题。"

### Q8：哪些地方体现了继承和多态？

> "六组继承：
> `BinaryFile` ← `MappedBinaryFile`、
> `InstructionDecoder` ← `X86_64Decoder`、
> `BasicBlockBuilder` ← `LinearBasicBlockBuilder`、
> `EdgeAnalyzer` ← `X86EdgeAnalyzer`、
> `AnalysisPass` ← 三个 Pass、
> `GraphWriter` ← `DotGraphWriter`/`TextWriter`。
>
> 而且多态是用在实处，不是摆着看的：
> 比如 `InstructionStream` 只认识 `InstructionDecoder*`，
> 换一个架构只要换派生类；
> `endsBlock()` 被派生类重写后，`ret` 也成了基本块的结束条件，
> 划分结果因此不同；main 里遍历 `AnalysisPass*` 数组，
> 新增分析不用改主流程。"

### Q9：如果二进制被 strip 了怎么办？

> "没有符号表就无法按名字定位函数。
> 我们先用 `.symtab`，找不到再试 `.dynsym`，
> 都没有就明确报错，并提示用 `--symbols` 看有哪些函数可用。
> 要支持 strip 过的程序，需要做函数边界识别，
> 比如解析 `.eh_frame` 或者按 `push %rbp` 特征扫描 —— 这是后续可以做的。"

### Q10：这个对软件安全有什么用？

> "控制流图是二进制分析的基础：
> 恶意样本分析要靠它理解行为、去混淆；
> 模糊测试用边覆盖率引导输入变异；
> 编译器优化建立在 CFG 上；
> CFI（控制流完整性）就是校验运行时控制流是否符合编译期算出的 CFG，
> 用来防 ROP 这类攻击。
>
> 我们现在这个框架里已经预留了栈分析、数据流分析、污点分析、
> 危险函数识别的接口，后面可以直接接着做漏洞分析实验。"

## 四、三句话记住全场逻辑

1. **输入** ELF 文件和函数名，**输出** Graphviz 控制流图，**全程不调用外部程序**；
2. **四步**：ELF 解析定位函数 → 自己解码机器码 → Leader 法划块 → 按块尾指令连边；
3. **六组继承**，每层都是抽象基类加派生类，main 里用基类指针驱动。
