int classify(int x)
{
    int sum = 0;
    int i;

    if (x > 100) {              /* 分支 1 */
        sum = 100;
    } else if (x > 0) {         /* 分支 2 */
        sum = x;
    } else {                    /* 分支 3 */
        sum = -x;
    }

    for (i = 0; i < 3; i++) {   /* for 循环：形成向后跳转边 */
        sum = sum + i;
    }

    return sum;
}

四、ELF 解析模块（自己实现）

只使用 Linux 系统头文件 <elf.h> 的结构体定义

Elf64_Ehdr / Elf64_Shdr / Elf64_Sym 等只是 ELF 格式的 数据布局描述，不是解析库。解析逻辑全部自己写。

4.1 文件访问：open → fstat → mmap

int fd = open(path, O_RDONLY);                                    /* 打开        */
fstat(fd, &st);                                                   /* 取大小      */
void *m = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);  /* 只读映射    */
... 分析全程只在映射区上进行 ...
munmap(m, size);  close(fd);                                      /* 析构时释放  */

选择 mmap 的原因：ELF 分析是"拿着偏移直接取字节"的场景， 映射后 data() + offset 就是指针，零拷贝；且 data() 与 size() 构成完整可访问区间，所有边界检查都基于这两个值。

4.2 文件头六项校验

检查项失败时的报错示例
长度 ≥ sizeof(Elf64_Ehdr)文件过小：40 字节，不足以容纳 ELF64 文件头（64 字节）
magic = 7f 45 4c 46不是 ELF 文件：magic 为 50 4b 03 04，应为 7f 45 4c 46
EI_CLASS == ELFCLASS64不是 ELF64（EI_CLASS = 1）
EI_DATA == ELFDATA2LSB不是小端 ELF（EI_DATA = 2）
EI_VERSION == EV_CURRENT不支持的 ELF 版本
e_machine == EM_X86_64不是 x86-64 目标文件（e_machine = 183）

4.3 函数定位：从符号到机器码

st_value（虚拟地址，来自符号表）
   │  找到 st_shndx 对应的节：secAddr = sh_addr, secOff = sh_offset
   ▼
offsetInSection = st_value - secAddr           ← 节内偏移
fileOffset      = secOff + offsetInSection     ← 文件偏移
code            = fileData + offsetInSection   ← 机器码首字节指针

以 classify 为例（实测）：st_value = 0x4011cd， .text 节 sh_addr = 0x401050、sh_offset = 0x1050， 故 fileOffset = 0x1050 + 0x17d = 0x11cd， 机器码内容为 55 48 89 e5 …（即 push %rbp; mov %rsp,%rbp），大小 81 字节。

4.4 四类边界情况都有处理

情况处理方式
符号未定义 / 特殊索引SHN_UNDEF、SHN_ABS 等直接视为"没有机器码"
st_size == 0GCC 的 _init 等常见；用"同节内下一个函数符号"或"节末尾"兜底推算
st_size 超出节范围截断到节内剩余空间并告警
机器码范围超出文件最后防线：拒绝并置 code = NULL

五、x86-64 解码器（本次升级的核心）

架构相关与架构无关的分界线

InstructionDecoder 是抽象基类，X86_64Decoder 是派生类。 上层（InstructionStream、CFG 各模块）只认识基类指针，完全不知道底下是什么指令集。 更换目标架构只需新增一个派生类，上层代码一行不改。

5.1 指令格式与解码七步

┌───────────────┬─────┬────────────┬───────┬─────┬───────┬──────┐
│ Legacy Prefix │ REX │  Opcode    │ ModRM │ SIB │ Disp  │ Imm  │
│  (0 或多个)    │(0/1)│ (1/2/3 字节)│ (0/1) │(0/1)│(0/1/4)│(0..8)│
└───────────────┴─────┴────────────┴───────┴─────┴───────┴──────┘
  1. Legacy 前缀：LOCK F0、REP/REPNE F2/F3、 段前缀 2E 36 3E 26 64 65、66、67（可重复、顺序任意）
  2. REX：40–4F，解析 W/R/X/B 四个扩展位
  3. Opcode：单字节，或 0F xx 两字节；0F 38 / 0F 3A 三字节明确报错
  4. ModRM：拆出 mod / reg / r/m
  5. SIB：仅当 mod≠3 且 r/m==4 时存在，拆出 scale / index / base
  6. 位移：由 mod 与 r/m 共同决定长度（见下表）
  7. 立即数：由 opcode 与 REX.W / 66 共同决定长度

5.2 长度是"推导"出来的，不是猜的

条件位移长度
mod == 0 且 r/m == 5disp32（RIP 相对寻址）
mod == 0、有 SIB 且 base == 5disp32（无基址）
mod == 1disp8
mod == 2disp32
mod == 3无位移（寄存器直接寻址）

两个易错点：SIB.index == 4 表示"没有变址"（不是 rsp）； SIB.base == 5 且 mod == 0 表示"没有基址"（不是 rbp）。 0x83 与 0x81 都是 Group1，但前者用 imm8 并符号扩展。

5.3 关键约束：绝不猜测未知指令的长度

x86 是变长指令集，长度算错一条，后面全部错位。 因此遇到不支持的 opcode 时，解码器立即返回失败， InstructionStream 停止该函数的解码并报出具体地址与 opcode 字节： 
[elfcfg] ERROR: 解码停止于 0x4012ab（函数内偏移 53）：不支持的 opcode 0F 28
已解出的部分仍然保留，可用于分析。绝不会把未知指令当作 1 字节继续解码。

5.4 操作数顺序：本项目踩过的坑

Intel 语法与 AT&T 语法的操作数顺序是相反的，本项目输出 AT&T 风格（带 % 与 $），因此需要交换：

机器码Intel 语法本项目输出（AT&T）
48 89 e5mov rbp, rspmov %rsp,%rbp
8b 45 ecmov eax, [rbp-0x14]mov -0x14(%rbp),%eax
89 45 fcmov [rbp-0x4], eaxmov %eax,-0x4(%rbp)

最初实现把顺序写反了，靠与 objdump 逐条比对才发现 —— 这也是保留交叉验证脚本的原因。

指令编码
短条件跳转 Jcc（16 种条件）70–7F rel8
近条件跳转 Jcc（16 种条件）0F 80–0F 8F rel32
无条件跳转 JMPEB rel8 / E9 rel32

数据传送与运算还支持：mov / lea / movzx / movsx / movsxd / push / pop / add / or / adc / sbb / and / sub / xor / cmp / test / not / neg / mul / imul / div / idiv / inc / dec / 移位 / xchg / cmpxchg / xadd / nop / leave / cwde / cdq / cmovcc / setcc / bswap / syscall / cpuid / rdtsc 等。

六、基本块识别模块

BasicBlockBuilder（抽象基类）　──▶　LinearBasicBlockBuilder（派生类）

算法：Leader（入口）法，与早期版本一致。

规则内容
规则 1函数的第一条指令是一个基本块的入口
规则 2跳转指令的目标地址是一个基本块的入口
规则 3跳转指令之后的下一条指令也是一个基本块的入口
补充ret / hlt 之后也另起一块，避免把不可达代码并进上一块

多态在这里的作用

/* 基类：只有跳转才结束基本块 */
int BasicBlockBuilder::endsBlock(const Instruction *ins) const {
    return (ins->type == INST_JMP || ins->type == INST_JCC ||
            ins->type == INST_LOOP) ? 1 : 0;
}
/* 派生类：x86 上 ret / hlt 也结束基本块 —— 划分结果因此不同 */
int LinearBasicBlockBuilder::endsBlock(const Instruction *ins) const {
    if (BasicBlockBuilder::endsBlock(ins)) return 1;
    return (ins->type == INST_RET || ins->type == INST_HLT) ? 1 : 0;
}
本例中：26 条指令 → 9 个基本块（B0 ~ B8）

七、基本块执行关系识别模块

EdgeAnalyzer（抽象基类）　──▶　X86EdgeAnalyzer（派生类）

核心观察：一个基本块的全部出边，只由它的最后一条指令决定。

块尾指令出边EdgeType 与目标
条件跳转 Jcc / LOOP2 条EDGE_BRANCH_TRUE（跳转目标）+ EDGE_BRANCH_FALSE（顺序下一块）
无条件跳转 JMP（直接）1 条EDGE_UNCONDITIONAL（不再顺序执行）
无条件跳转 JMP（间接）1 条EDGE_INDIRECT（目标不可静态确定，to = NULL）
RET / HLT0 条函数出口，控制流终止
块尾是 CALL1 条EDGE_CALL（返回后继续的下一块）
其它（含块内 call）1 条EDGE_FALLTHROUGH
关于图中的红色加粗边：判定方式是"目标块地址 ≤ 源块地址"，说明控制流往回跳。
需要说明的是，严格意义的 CFG back edge 需要用支配关系判定（目标块支配源块）， 本实现未构造支配树，因此这是向后跳转边的演示性近似， 代码与文档中统一称为 backward jump hint。 在 classify 中，这条 B7 → B6 确实对应源码的 for 循环。
本例中：9 个基本块 → 11 条基本块执行关系（其中 1 条为向后跳转边）

九、输出层

GraphWriter（抽象基类）　──▶　DotGraphWriter / TextWriter

输出层只依赖 ControlFlowGraph，不关心它是怎么来的。 同一个 CFG 既能输出成 Graphviz DOT（交给外部 dot 渲染），也能输出成人类可读的文本。

  • 节点：每个基本块一个方框，框内逐行列出该块的每条指令（地址 + 助记符 + 操作数）
  • 边：每条执行关系一个箭头，标签为触发该分支的指令（jle / jmp / fall）
  • 配色：入口块绿色、以 ret 结尾的出口块红色、向后跳转边红色加粗、不可达块灰色虚线框
  • 间接跳转：画成虚线的悬挂边，明确表示"目标不可静态确定"
程序不依赖 Graphviz 库：elfcfg 把 DOT 写到 stdout 后即运行结束； dot -Tpng 属于程序外部的展示步骤，不参与任何分析。
./elfcfg demo classify > classify.dot　然后　dot -Tpng classify.dot -o classify.png

多态不是形式上的：
① InstructionStream 只认识 InstructionDecoder*，换架构只需换派生类；
② endsBlock() 被派生类重写后，ret 也成了基本块的结束条件，划分结果因此不同；
③ analyzeBlock() 基类只连顺序边，派生类加入 x86 跳转语义；
④ main 遍历 AnalysisPass* 数组，新增分析 pass 不必改主流程；
⑤ 所有基类都声明了虚析构函数，保证 delete 基类指针 时资源正确释放。

序言、sum=0、if (x>100)B0　0x4011cd – 0x4011e1块尾 jle，产生两条出边
sum = 100;B1　0x4011e1 – 0x4011ea块尾 jmp，无 fall 边
else if (x > 0)B2　0x4011ea – 0x4011f0块尾 jle，两条出边
sum = x;B3　0x4011f0 – 0x4011f8块尾 jmp
sum = -x;B4　0x4011f8 – 0x401200顺序落入 B5
分支汇合、for 初始化B5　0x401200 – 0x401209块尾 jmp
循环体 sum += i; i++B6　0x401209 – 0x401213循环体
循环条件 i < 3B7　0x401213 – 0x401219块尾 jle，向后跳转边来源
return sum;B8　0x401219 – 0x40121e块尾 ret，无出边
读图提醒：汇编中的 jle 含义是"小于等于就跳走"，因此对条件跳转而言， 跳转边对应的是源码条件"不成立"，fall 边才对应源码条件"成立" —— 两者方向相反。

十四、已知限制（如实记录）

#限制现象 / 影响
1解码器非完整实现不支持三字节 opcode（0F 38 / 0F 3A）、SSE/AVX、x87 浮点、位操作指令；遇到即报错停止
2间接跳转目标不可解析jmp *%rax 生成 EDGE_INDIRECT 边，目标块为空，可达性分析会漏掉经由该边到达的块
3switch 跳转表能识别为间接跳转，但不读跳转表内容，各 case 对应的块会被误判为不可达（见 --text demo switch_test）
4"向后跳转边"是演示性近似判据为"目标地址 ≤ 源地址"，不是严格 back edge（严格需支配关系）；统一称 backward jump hint
5依赖符号表strip 后的二进制无法按名字定位函数，会明确报错并提示用 --symbols 查看可用函数
6其它只支持 ELF64 小端 x86-64；只分析函数内部 CFG；不解析 .eh_frame；不处理重定位

14.2 现实意义

控制流图是软件安全领域的基础分析手段：恶意代码分析中用它理解样本行为与去混淆； 模糊测试（如 AFL）用边覆盖率引导输入变异；编译器优化的数据流分析建立在 CFG 之上； 控制流完整性（CFI）防护通过校验运行时控制流是否符合编译期算出的 CFG，来抵御 ROP 等攻击。 本练习实现的正是这条技术链路的第 0 步 —— 而且是从 ELF 字节流开始的第一步。
